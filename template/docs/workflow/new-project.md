# 新项目流程

从空目录开始的项目按本流程走到：工作流验收通过、项目骨架有真实的验证命令和领域规则、基线已提交，之后进入日常开发。入口是 `/workflow-new`，它按 `workflow-new-project` 技能分阶段进行，需要你决定的地方逐个询问；中断后重新运行，会按项目现状判断进行到哪一步。

已经用脚手架生成过代码的项目按已有项目接入，使用 `/workflow-setup`，见 [接入向导](onboarding.md)。

## 阶段总览

| 阶段 | 做什么 | 由你决定 | 完成标志 |
| --- | --- | --- | --- |
| 0 准备 | 在 OpenCode 之外新建目录、`git init`、复制整个模板、运行 `setup.mjs`、在项目根启动 opencode | 是否安装 OpenCode | 插件 active，`/workflow-new` 可用 |
| 1 最小接入与基线提交 | 用 `/workflow-setup` 跑第一轮；基线提交到默认分支 | 模式、Superpowers 范围、模型、组件；基线提交 | finish 通过；已有提交且工作区干净 |
| 2 设计 | 新建分支；按设计清单确定需求、技术栈和骨架；写设计记录和项目概要初稿 | 设计清单各项 | 设计经你确认；设计记录与项目概要初稿已提交 |
| 3 搭骨架 | 按选定方式落地，合并同名文件，安装依赖，运行验证命令 | 落地方式、依赖安装 | 骨架清单齐全；验证命令实际通过；已提交 |
| 4 项目规则 | 补全项目概要；领域规则与 `scopes.json`；审核分区；pipefail；`.gitignore`；保护规则的拟议差异 | 提交格式；`protection.json` 由你在 OpenCode 之外修改 | doctor 没有 fail；领域规则能加载；已提交 |
| 5 第二轮配置 | 再跑 `/workflow-setup`：按领域规划子代理，选择组件 | 子代理、组件、脚手架带来的 AI 配置 | finish 通过；已提交 |
| 6 验收与交接 | 原生冒烟；可选 `/review`；合并到默认分支；交付清单 | 是否审核、合并方式 | 交付清单已给出；默认分支包含全部提交；工作区干净 |

小项目各阶段可以很短，例如只有一个领域、不新增子代理，但不跳过需要你确认的点。推送、创建远端仓库和发布不在本流程内。

## 第 0 阶段：准备

在 OpenCode 之外执行；让模型代为执行时，全局安装仍需你确认。在新建的空目录中运行下面的命令，`<套件目录>` 是完整工作流套件的位置。也可以从刚在 GitHub 等处建好、只有 README、LICENSE 或 `.gitignore` 的仓库开始：复制会覆盖同名文件，已有 `.gitignore`、`.gitattributes` 时先改名（例如 `.gitignore.orig`），第 1 阶段由模型把其中的条目并入模板的同名文件，再删除改名的文件。

Linux、macOS、WSL：

```bash
git init
cp -a "<套件目录>/template/." .
node scripts/workflow/setup.mjs
opencode
```

Windows（PowerShell）：

```powershell
git init
Copy-Item -Recurse -Force "<套件目录>\template\*" .
node scripts\workflow\setup.mjs
opencode
```

复制包括隐藏文件，路径含空格时保留引号。默认分支名用 main 或 master；用其他名称时，之后的 `/review` 需要显式提供 base。确认 `workflow.starter` 已加载且为 active 后运行 `/workflow-new`。

## 第 1 阶段：最小接入与基线提交

由 `/workflow-setup` 跑第一轮，按 [接入向导](onboarding.md) 选择模式、Superpowers 安装范围和模型策略。新项目的建议：

- 既有 AI 配置：空项目通常没有；个人目录中的条目照常报告。
- 子代理：先不新增，第 5 阶段按领域规划。
- 组件：质量、CI、发布、MCP 先都不选，它们依赖技术栈的工具和命令，第 5 阶段再选；你坚持选择时照常处理。

完整模式在 Superpowers 实际可用、本会话读取 brainstorming 和 writing-plans 之前不进入第 2 阶段。verify、finish 通过后做基线提交：先列出要提交的文件（模板、`onboarding.json` 和向导写入的配置），你确认后分两次工具调用暂存和提交到当前分支。没有任何提交时 `/review` 无法运行；第 6 阶段的审核以这个提交为起点。

## 第 2 阶段：设计

新建分支（例如 `project-start`），在主检出中进行。不使用工作树：本流程会多次修改 `opencode.jsonc` 和接入档案，工作树中的这些文件与主检出各自独立。

- 完整模式读取 brainstorming，按其流程产出设计并经你确认；之后用 writing-plans 写的计划只覆盖骨架，功能实现留到流程结束后。Superpowers 建议使用工作树时，同样在主检出的分支上进行。设计记录沿用 brainstorming 的位置（默认 `docs/superpowers/specs/`）。
- 基础模式按下面的清单逐项在对话中确认，确认后写设计记录，默认 `docs/design.md`，你可以改位置。

设计清单（两种模式相同）：

1. 用途、用户和核心场景；不做什么。
2. 技术栈与版本：语言和运行时版本、框架、包管理器。你有偏好时记录并核实本机可用；没有时比较 2–3 个方案，由你选。
3. 目录与领域：每个领域的职责和依赖方向；哪些是生成物、第三方代码，以及它们的生成或升级入口。
4. 验证命令：安装、静态检查或类型检查、测试、构建，以及各自的工作目录。首命令不在守卫支持清单内时改用支持的入口（例如 `python -m`、`npx`、`bundle exec`），见 [守卫说明](../../.opencode/workflow/checks/README.md)。
5. 配置与凭据：需要的环境变量、`.env.example` 的内容、新增的凭据文件形式。
6. 骨架清单与落地方式：要创建的目录、清单文件、最小可运行入口、至少一个冒烟测试；选用下文三种落地方式中的哪一种。

设计确认后，在根 `AGENTS.md` 的项目概要一节写入初稿：用途、技术栈、设计记录的位置及何时阅读。本阶段的改动经你确认后提交。

## 第 3 阶段：搭骨架

- 按设计选定的方式落地，合并同名文件，规则见下文“骨架落地方式”。
- 骨架由主代理直接实施；需要派发时按 [开发与协作](development.md) 使用 implementer。
- 用设计中的包管理器安装依赖。新装语言工具链（如 uv、cargo）后，由你在终端执行 `opencode service restart`，再重新运行 `/workflow-new`：后台服务的 PATH 在启动时确定，不重启就找不到新工具；守卫不放行 `opencode` 命令，重启也会中断当前会话。
- 运行设计中的全部验证命令，都要实际执行成功。测试命令要实际执行至少一个用例：输出中能看到执行的用例数或用例名；零个用例或全部跳过不算通过，见 [测试与证据](testing.md)。

完成后经你确认提交。

## 第 4 阶段：项目规则

- 根 `AGENTS.md` 的项目概要补全：目录与领域、验证命令入口（写包脚本或命令入口，不展开长命令）、设计记录位置。保持简短。
- 询问提交格式，写进 `docs/workflow/development.md` 中“按项目约定的提交格式”处。
- 领域规则：按设计中的领域写 `<目录>/AGENTS.md`（职责与依赖、契约、修改与验证、生成物），在 `.opencode/workflow/scopes.json` 登记映射，首次编辑该领域时确认规则被加载。只有一个领域时只用根规则。
- 审核路由：`.opencode/workflow/review/routing.json` 增加领域分区；按风险新增检查单并登记到 `catalog.json`；未知路径保守进入 common。
- pipefail：内置识别以外的测试命令前缀登记到 `.opencode/workflow/pipefail.json`。
- `.gitignore`：补充构建产物、依赖目录、缓存和本地配置。
- 保护规则：生成目录、第三方目录、新的凭据文件形式，由模型给出 `.opencode/workflow/protection.json` 的拟议差异和理由，你在 OpenCode 之外修改；之后模型运行 `node scripts/workflow/doctor.mjs --print-permissions`，用输出更新 `opencode.jsonc` 末尾的权限块。没有需要新增的规则时说明理由。
- 运行 `node scripts/workflow/doctor.mjs`：fail 必须处理，warn 逐项处理或说明。

完成后经你确认提交。

## 第 5 阶段：第二轮配置

再跑一次 `/workflow-setup`，已有选择先展示：

- 脚手架带来的 `CLAUDE.md`、`.cursor/` 等其他 AI 工具配置，在既有配置阶段决定迁移或保留。
- 子代理规划按第 4 阶段登记的领域建议，可以不新增。
- 组件：质量扩展（登记第 4 阶段确定的格式工具和文件关联）、接入方 CI（依赖完整质量扩展）、发布与 MCP 按需。复制扩展时以完整套件目录作为来源；第 0 阶段放在临时目录的套件已被清理时，重新获取同一版本。

verify、finish 通过后经你确认提交。

## 第 6 阶段：验收与交接

- 原生冒烟：用合成临时文件验证普通编辑、受保护路径被拒绝、已登记领域的规则加载（只有根规则时核对根规则的加载）、测试管道的失败保留；验证后删除临时文件，不读取或复制真实凭据。
- 可选 `/review`，由你触发：在分支上审核从基线提交到当前的全部改动，显式提供基线提交作为 base（仓库已有远端或更早的提交时，默认分叉点不是它，审核会包含整个模板）；有阻断时修复后按同一 base 重新运行，见 [审核策略](review-policy.md)。
- 合并到默认分支：方式由你决定，例如 `git switch main` 后 `git merge --ff-only project-start`；是否删除分支也由你决定。不推送。
- 交付清单：已配置、已加载、已验证、未验证；设计记录位置；验证命令及实际结果；保护规则的拟议差异是否已应用；下一步怎么用：新需求如何进入设计和计划、问题如何调试、如何 `/review`、如何重新运行 `/workflow-setup` 和 doctor。新功能在分支上开发，`/review` 才能按分叉点审核。

## 骨架落地方式

| 方式 | 适用 | 做法 |
| --- | --- | --- |
| 子目录脚手架 | 独立应用（Web、服务等） | 在 OpenCode 中带齐非交互参数运行，生成到新的子目录（如 `web/`） |
| 手写骨架 | 库、CLI、小服务 | 模型直接创建清单文件、源码与测试目录 |
| 你在终端运行 | 脚手架必须交互，或首命令不在守卫支持清单内（如直接调用 `django-admin`） | 你在自己的终端运行；完成后模型核对结果并合并冲突文件 |

三种方式共同遵守：

- 不在项目根使用覆盖或清空目录的参数，否则会删掉模板文件。
- 脚手架带来的 `.gitignore`、`.gitattributes`、README、`AGENTS.md` 与模板合并，不整体替换。
- 不在子目录中新建 `.git`：嵌套仓库里的文件不会作为普通文件进入提交，凭据扫描和 `/review` 都覆盖不到。发现时停下来由你处理。
- 脚手架生成的 `.env` 模型读不到，这是保护规则的预期效果；配置示例写进 `.env.example`。
- 守卫不展开通配符：移动或复制文件时逐个写明路径。

本文不列各技术栈的脚手架命令：参数随版本变化，在设计阶段按实际版本核实。

## 其他规则

- OpenCode 的 `/init` 会创建或更新根 `AGENTS.md`。新项目的根规则由本流程补充；确实要用时先核对差异，保留工作流的章节。
- 完整模式缺技能时停在第 1 阶段处理安装与重载，不模拟技能。
- 基础模式的设计按清单在对话中确认，其余阶段与完整模式相同。

## 中断后恢复

重新运行 `/workflow-new` 时，按下列事实判断进行到哪一步，先说明判断及依据，经你确认后从该阶段继续，不重做已完成的阶段：

| 核对的事实 | 未完成的阶段 |
| --- | --- |
| `workflow_setup status` 没有接入选择记录 | 第 1 阶段 |
| 模板还没有提交（`git log -1 -- .opencode` 没有输出） | 第 1 阶段的基线提交 |
| 根 `AGENTS.md` 的项目概要仍是占位说明 | 第 2 阶段 |
| 设计记录中的骨架清单不全，或验证命令没有实际通过 | 第 3 阶段 |
| 项目概要缺验证命令，或设计中的领域没有登记到 `scopes.json` | 第 4 阶段 |
| 第二轮配置是否完成（向导档案不区分轮次） | 第 5 阶段，直接问你 |
| 有未提交的改动、分支未合并或没有做原生冒烟 | 第 6 阶段 |

完整模式下，`status` 因本会话还没有读取 brainstorming、writing-plans 而未就绪时，在本会话读取后继续，不算回到第 1 阶段；脚手架带来的其他 AI 配置尚未决定时，留到第二轮配置处理。判断不清时询问，不猜测。
