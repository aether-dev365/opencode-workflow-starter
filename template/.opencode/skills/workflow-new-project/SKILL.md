# 新项目流程

在主会话中使用。先阅读 `docs/workflow/new-project.md`，再调用 `workflow_setup status`。AI 负责调查、解释、提问和实施；接入配置交给 `/workflow-setup` 的工具预览、应用和验收。

## 适用范围

从空目录开始、走本流程建立的项目。模板以外已有构建清单（如 `package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml`；模板自带的 `.opencode/plugins/workflow/package.json` 不算）或源码文件，而根 `AGENTS.md` 的项目概要仍是占位说明、为空或没有这一节时，先问用户继续新项目流程，还是改用 `/workflow-setup` 按已有项目接入。

## 每次回答的结构

先用一句话说明判断出的阶段及依据，再提出本阶段唯一需要的决定，最后说明影响哪些文件、范围或费用。优先使用原生 `question` 工具，缺失时用普通对话等待明确答复。取消、没有答复或无法交互时停在当前阶段。

## 判断当前阶段

开始和每次重新进入时核对下列事实，先展示判断及依据，经用户确认后从该阶段继续，不重做已完成的阶段。完整模式下 `status` 因本会话还没有读取 brainstorming、writing-plans 而未就绪时，在本会话读取后继续，不算回到第 1 阶段；脚手架带来的其他 AI 配置尚未决定时，留到第二轮配置处理。判断不清时询问，不猜测。

| 核对的事实 | 未完成的阶段 |
| --- | --- |
| `workflow_setup status` 没有接入选择记录 | 最小接入与基线提交 |
| 模板还没有提交（`git log -1 -- .opencode` 没有输出） | 最小接入与基线提交（基线提交） |
| 根 `AGENTS.md` 的项目概要一节只有占位说明 `（接入时填写，保持简短：用途、技术栈、目录与领域、验证命令入口，以及设计记录的位置和何时阅读。）` 或为空 | 设计 |
| 设计记录中的骨架清单不全，或验证命令没有实际通过 | 搭骨架 |
| 项目概要缺验证命令，或设计中的领域没有登记到 `scopes.json` | 项目规则 |
| 第二轮配置是否完成（向导档案不区分轮次，询问用户） | 第二轮配置 |
| 有未提交的改动、分支未合并或没有做原生冒烟 | 验收与交接 |

## 阶段检查单

0. **准备**：在 OpenCode 之外完成（新建目录、`git init`、复制整个模板、`setup.mjs`、启动 opencode）。工具或插件缺失时按流程文档的准备阶段处理，不编造结果。
1. **最小接入与基线提交**：加载 `workflow-onboarding` 技能跑第一轮 `/workflow-setup`，finish 通过后回到本技能。给向导的新项目建议：子代理先不新增（`agents: []`）；质量、CI、发布、MCP 先都不选，说明第二轮再处理；用户坚持时照常处理。完整模式在 Superpowers 实际可用、本会话读取 brainstorming 和 writing-plans 之前不往下走。复制前改名保存的 `.gitignore`、`.gitattributes` 等，把其中的条目并入模板的同名文件后删除改名的文件。然后列出要提交的文件，用户确认后分两次工具调用暂存和提交到当前分支（main 或 master）。
2. **设计**：新建分支（例如 `project-start`），在主检出中进行，不用工作树。完整模式按 brainstorming 产出设计，writing-plans 的计划只覆盖骨架；基础模式按流程文档的六项设计清单逐项确认，设计记录默认写到 `docs/design.md`。设计确认后在项目概要写入初稿：用途、技术栈、设计记录位置及何时阅读。
3. **搭骨架**：按设计选定的落地方式（子目录脚手架、手写骨架、用户在终端运行）实施，遵守流程文档“骨架落地方式”的共同规则；安装依赖；全部验证命令实际通过，测试至少实际执行一个用例。
4. **项目规则**：补全项目概要和验证命令入口；询问提交格式，写进 `docs/workflow/development.md`；领域 `AGENTS.md` 与 `scopes.json`、审核分区、pipefail、`.gitignore`；保护规则给出拟议差异；运行 doctor。
5. **第二轮配置**：再次加载 `workflow-onboarding` 技能跑 `/workflow-setup`：按第 4 阶段登记的领域规划子代理，选择组件，处理脚手架带来的其他 AI 配置；finish 通过。
6. **验收与交接**：原生冒烟；用户需要时由其触发 `/review`，以基线提交为 base；用户决定合并方式后合并到默认分支；给出交付清单。

第 2 到第 5 阶段结束时，本阶段的改动经用户确认后在分支上提交。

## 边界

- 设计未经用户确认不搭骨架；不把脚手架或安装脚本的默认值当成用户选择。
- 不推送、不发布、不创建远端仓库。
- `protection.json` 只给拟议差异和理由，由用户在 OpenCode 之外修改。
- 完整模式缺技能不模拟；只使用工具实际返回的事实。
- 普通实现和提交不自动派模型审核。

## 交付

交付清单分别列出：已配置、已加载、已验证、未验证；设计记录位置；验证命令及实际结果；保护规则的拟议差异是否已应用；下一步如何使用：新需求如何进入设计和计划、问题如何调试、如何用 `/review` 正式审核、如何重新运行 `/workflow-setup` 和 doctor。之后的新功能在分支上开发。
