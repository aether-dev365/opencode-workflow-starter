# 引导式接入

在主会话中使用。先阅读 `docs/workflow/onboarding.md`，再调用 `workflow_setup status`。AI 负责解释和提问，工具负责预览、应用和验收；reviewer 不能安装。

## 每次回答的结构

先用一句话说明检测到的现状，再提出当前阶段唯一需要的决定，最后说明该决定会影响哪些文件、范围或费用。优先使用原生 `question` 工具；缺失时用普通对话等待明确答复。取消、没有答复或无法交互时保留未完成状态，不安装。

## 按检测结果推进

1. **既有 AI 配置**：status 的 `existing` 列出项目里其他 AI 工具的配置及其在 OpenCode 中是否生效。逐项阅读后说明用途、与本工作流的重叠或冲突、建议迁移还是保留及理由，评估要点和凭据读法见接入文档；按工具分组用 `question` 多选“要迁移的项”，未选为保留，取消为未决定。决定写入 SetupChoices 的 `existing`，键用 path 原样；迁到 `.opencode/commands`、`.opencode/skills` 的目标路径同时记为保留；没有检测项时一句话带过。检测未完成时转述原因和处理建议，用户处理后重新 status，不跳过检测。
2. **模式未确定**：先解释“完整流程（推荐，要求 Superpowers）”和“基础保护（不要求外部技能）”，询问选择。“按推荐安装”不是已经回答了模式与全局范围。已经明确的答案先展示，不重问。
3. **完整模式的 Superpowers 来源**：status 的 `superpowers.installed` 列出已登记的 Superpowers。已登记但 `available` 为 false 时转述 `issues`，加载失败的还要转述 `installed` 中的 `error`，用户处理并重载后重新 status。接入前就已经可用的安装（固定版本或其他版本，项目级或个人全局），SetupChoices 的 `superpowers` 记 `existing`；`pinned` 为 false 时先说明这是未经套件验收的版本及其来源和版本，询问沿用、人工移除后改装固定版本，还是改用基础模式，不静默升级或降级。没有登记时，先询问项目级安装（推荐）或个人全局安装，说明 Superpowers 会注入工作方法规则，记 `project` 或 `global`；用 `bootstrap` 生成该范围计划，展示文件与影响，用户确认后才 `apply`，以 `planID` 传递同一 id。等待安装及配置重载后重新 status；已记的 `project` 或 `global` 保持不变，不因安装后已经可用而改记 `existing`，它们要求实际加载的是固定版本。此前不进入设计/实施计划，也不模拟技能。
4. **完整模式技能可用**：按阶段使用原生 `skill` 工具读取 `brainstorming` 和 `writing-plans`，遵守其确认边界。OpenCode V2 的参数是 `id`，以实际 Schema 为准。来源、正文和本会话成功读取都要成立；同名条目、磁盘文件或其他会话读取不算。错误、重载、Location 切换或压缩后，按工具报告重新读取缺失技能。
5. **子代理规划**：根据项目领域、目录与工作区结构、技术栈和决定迁移的子代理，建议新增几个实现类子代理（可以不新增），用表格说明名称、职责、依据和建议的模型策略，再用 `question` 多选；用户可以改名或改职责。明确不要时写 `agents: []`，取消则停在本阶段。不新增审核类子代理，审核视角用检查单扩展。由新项目流程（`/workflow-new`）调用的第一轮还没有领域时建议不新增，说明第二轮再规划。
6. **模型策略**：展示 status 检测到的主会话模型与候选，不让用户重复辨认可检测事实。分别询问 implementer、reviewer 和新增子代理动态继承还是固定 ID，可以先问是否全部继承。用户已经说“跟主模型”就记录 inherit，不再要求挑选固定模型。选固定且该模型的 `variants` 非空时，再询问思考强度：列出这些 variant 和“默认（不指定）”，选中的写成 `provider/model#variant`；主会话当前 variant 可以标出，但不代选。没有选择就不写 variant，使用模型默认，不沿用主会话的思考强度。继承时子代理跟随主会话的模型和思考强度，不能单独指定；要单独指定就改选固定。固定当前 ID 不等于继承；模型可见不等于认证调用成功，不自动发起付费探测或收集 API key。核对上级配置与代理文件覆盖，保留 reviewer 只读权限。
7. **组件**：质量选择 off/checks/hook，解释本地 hook 只提醒、不拦截、不自动修复；CI 依赖质量但不要求本地 hook，冲突时请用户取舍。发布与 MCP 默认不新增，需要时协助填写实际配置，未完成就列待处理；不根据示例启用生产操作。off 表示不新增、不卸载，已有内容显示保留。由新项目流程调用的第一轮建议先都不选，说明技术栈确定后的第二轮再选；用户坚持时照常处理。
8. **确认应用**：完整答案形成 SetupChoices 后调用 `plan`，复制扩展时提供完整套件 source。先展示模式、既有配置的决定及其影响、plan 返回的子代理全文、模型及各角色思考强度（`effort`）、全部组件、文件、全局影响、冲突和人工任务，再请求批准具体 id 并 `apply`。计划过期重新预览确认；权限拒绝后停止，不用 CLI 绕过。CLI 仅供单独授权的手动/非交互执行。
9. **执行迁移**：应用后按决定逐项迁移，每项先展示差异或新文件全文，确认后再写入；原文件保留，能共用的改为引用，删除须用户逐项明确要求；`protection.json` 只给拟议差异。完成后重新 `verify`。
10. **验证完成**：调用 `verify`，处理 issues（包括受管子代理的实际加载和有效模型），再调用 `finish`。基础模式也需要完成验收，但不能因此强制安装 Superpowers。只使用工具实际返回的事实，不提交自造 verified/ready 标志。

## 恢复与交付

重新进入时展示已保存选择和待应用计划，只处理新出现的既有配置；已确认的答案可保存在已确认被 Git 忽略的 `.opencode/workflow/.state/onboarding/answers.json`，草稿不等于批准。重载后只重验失效证据，不重做已应用文件或重复询问全部选项。

交付清单必须分别列出：已配置、已加载、已验证、未验证、下一步如何使用。说明新需求如何进入设计/计划、问题如何调试、如何用 `/review` 正式审核、如何重新打开 `/workflow-setup` 及运行 doctor。

模型策略不是额外多代理调用授权。普通实现不自动派模型审核；Superpowers 阶段自检不能替代本套件结构化 `/review` 或授予发布许可。业务测试、远端 CI、模型实际调用、真实发布和 MCP 服务端只读权限，没有独立证据就保留未验证。
